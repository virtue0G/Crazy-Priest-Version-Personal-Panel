## 1. 产品定位

**这不是记录工具，是能力增强系统。**

记录只是原料。系统的使命是把日常记录转成两样东西：

1. **看清**——你的水平、缺口、组合、状态（诊断）
2. **推进**——让你真的做出东西来（补强 → 验证 → 沉淀）

目标用户：有记录习惯、追求自我提升的主动学习者。**首版单用户**，但架构为多用户预留（见 §11）。

**首版要解决的真问题**（来自真实访谈）：

| 现状 | 系统的回答 |
|---|---|
| 知识储备足，但"懂却做不动" | 两轴诊断：道境不低，卡在**修为** |
| 目标大而模糊，迟迟无法启动 | **今日一炼**：每天只给一件具体的小事 |
| 可投入的精力与时间有限 | 修为优先：**先回元，不炼蛊** |
| 想学的太多 | **空窍有限**，系统负责砍，而不是加 |
| 缺少外部裁判，水平易虚高 | **AI 测考 + 费曼复述**；**境界由事件证明** |

---

## 2. 两条铁律

1. **事实层不可虚构。** 任何结论（进步、水平、缺口、晋升）必须能溯源到具体记录。做不到溯源的话，宁可不说。
2. **叙事层只换说法，不加事实。** 「晋升大师」必须由真实事件触发；报告同时给出「境界」与「考据证据」两栏，用户可核对。

> 这两条是整个系统的信用地基，也是它与"打卡 App / 心情日记"的分水岭。

## 3. 架构：两层 + 一个飞轮

```
┌─ 叙事层（风格包，可切换）─────────────────┐
│  蛊道 / 修仙 / 科幻 / 战锤 ……（只负责命名与呈现）│
├─ 事实层（世界无关，不可虚构）──────────────┤
│  道 · 蛊 · 修为 · 道境 · 道痕 · 证据 · 状态     │
└──────────────────────────────────────┘
                    ▲
                    │ 回写
   ┌────────────────┴─────────────────┐
   │  增强飞轮                          │
   │  ① 记录 → ② 结构化 → ③ 诊断        │
   │      ↑                    ↓        │
   │  ⑥ 沉淀 ← ⑤ 验证 ← ④ 补强          │
   └──────────────────────────────────┘
```

**③④⑤ 是"增强"发生的地方**，也是本产品的核心。

- **③ 诊断**：判水平、找缺口、看组合、读状态
- **④ 补强**：出题考你、生成练习、讲解、推荐、把知识变任务
- **⑤ 验证**：判你的产出，作为等级证据

**贯穿三者的核心操作是「养 · 炼 · 用」**（见 §4.6）：

| | 含义 | 系统对应动作 |
|---|---|---|
| **养** | 学习 · 输入 | 记录、喂料 |
| **炼** | 深化 · 加工 | 复习、拆解、合炼 |
| **用** | 实践 · 输出 | 做东西、解决真问题 |

## 4. 核心概念与字段（事实层）

### 4.1 道 Dao（开放集合）

- **万物皆有道**，道是开放集合，可随时添入。
- 三层：**主修**（1 条，决定称号）／**常修**（若干）／**游历**（不限，只记不追）。
- 字段：`name` `domain` `layer` `realm_index` `active`

### 4.2 蛊 Gu

- **蛊 = 一条道理 / 一个方法**的具象。分**凡蛊**（可学可买）与**仙蛊**（唯一，不可复制）。
- **硬约束：蛊师阶段只持有凡蛊。** 仙蛊之名不可用于自身之蛊（首版仅"在炼的那一只"例外）。
- 字段：`name` `dao_id` `tier` `kind` `is_vital`（本命）`fed_at` `state`

### 4.3 两轴

| 轴 | 字段 | 回答 |
|---|---|---|
| **修为** | `cultivation_rank`（一转～九转）＋空窍/真元/元石 | **能不能** |
| **道境** | 每条道各自的 `realm_index` | **懂不懂** |

- **修为是道境的天花板**：蛊师阶段大多只到「普通」，个别优秀者五转才达「大师」。
- **道境反过来放大修为**：同一份真元，道境越高效果越强。
- **判定按实，宁低不高**；「普通」是常态，不是贬低。

### 4.4 道痕 Dao Mark

- **可数、只增不减**的积累证据。**记努力，不直接兑换境界。**
- **计痕原则：不以"是否独立"论，以"是否获得经验"论**（"协作增加经验，推动道行"）：

  | 情形 | 计痕 |
  |---|---|
  | **产出**（方案/方法论/作品/结论，**含 AI 协作**） | 1–3 |
  | **踩坑律 / 深度复盘** | 0.5–2 |
  | **参与协作**（即使他人主导） | 0.1–0.5 |
  | **学习/输入**（**含搬运整理**——交给 AI 整理记忆也算） | 0.1–0.5 |
  | **愿望/待办** | 0 |

  > ★ **「纯搬运」档已取消**。收集资料并交给 AI 整理，本身就是扩展能力边界的动作。
  > **硬要求：AI 必须「整理并反馈」，不能只做存储**——只存不化，搬运就白费。这条约束直接决定 §6.2／§6.4 的实现质量。

- **★「道痕宽，境界严」是一对互补设计**：道痕记录你走过的路（含别人带着你走的），所以不会虚高；境界只认你自己打出来的，所以不被污染。
- **权重由用户确认**，AI 只做建议。

**★ 计痕前置闸门：抽取三分类**（不做则道痕严重虚高）

| 类别 | 判据 | 处理 |
|---|---|---|
| **自产** | 自己原创、亲历得出的 | 计道痕；**才可作晋升证据** |
| **抄录** | 收集、整理的外部资料 | 计知识，**不计道痕** |
| **愿望** | 想做但还没做的 | 记为**缺口/目标**，不算已有资产 |

> 这是首轮真实验证暴露的最大问题：把"文件里有的"当成了"本人的能力"，导致 5/18 条误判。

### 4.5 境界 Realm（★ 由事件证明，不可自评）

七级：**普通 → 大师 → 宗师 → 大宗师 → 准无上大宗师 → 无上大宗师 → 道主**

**规则**：
- 每个境界挂一组**证明事件**；事件未达成，境界就停在原处。
- **AI 不得自行判定晋升**——只能"提出证据、建议晋升"，**由用户确认后写入**。
- 事件一经确认，写入 `realms_log` 并永久可溯。

**首版六道的晋升（大师）事件**（各道本义，可迭代）：

| 道 | 蛊 | 晋升「大师」须达成 |
|---|---|---|
| 炼道 | 火候蛊 | 能**合炼出一只新蛊**，且它真能用 |
| 智道 | 因果蛊（本命） | 识破一条**一直起作用却无人命名**的规律，并为它命名 |
| 星道 | 先见蛊 | 对一个**长期走向**做出判断，且时间验证了它 |
| 阵道 | 铺路蛊 | 你布的阵在**你不在场时**依然运转 |
| 律道 | 准绳蛊 | 你立的一条律条**改变了之后的行为**（同错不再犯） |
| 音道 | 人言蛊 | 你说的话**被人复述、引用或据以行动** |

> **★ 待深化**：用户明确要求——**对各道内涵的理解要持续深化**。上表是 v1，属活文档，可迭代。

### 4.6 养 · 炼 · 用 与饿死

- 每只蛊有**饱食度**，由 `fed_at` 与当前时间推出：

  | 状态 | 判据（多久未「养」） |
  |---|---|
  | 饱食 | ≤ 2 周 |
  | 微饥 | 2 周 – 1 个月 |
  | 饥饿 | 1 – 3 个月 |
  | 濒死 | 3 – 6 个月 |
  | 饿死 · 沉睡 | > 6 个月 |

- **饿死 ≠ 遗忘，是沉睡**——可唤醒，但更费力。
- 系统在「微饥」起提醒，但**提醒要轻**，不制造焦虑。

### 4.7 杀招 Killer Move

- **多蛊合炼**的组合产出 = 真正的"技能搭配"。
- 状态：`构想` → `材料齐备` → `在炼` → `已成`
- 系统职责：
  - **合炼建议**：提示"你这几只蛊可以合成什么"
  - **逆推**：把现有强项拆开，看清它由哪几只蛊构成
- **首版已知杀招**：
  | 杀招 | 材料 | 状态 |
  |---|---|---|
  | **AI 分析工具**（data analytic for ai agent） | 火候蛊 × 因果蛊 × 铺路蛊 × AI | **兴趣最强**——07/20 即已写下此念，从未展开 |
  | **知识地图** | 因果蛊（智道）× 铺路蛊（阵道）× 人言蛊（信道） | 材料齐备——把随手记的知识与所学**串联成图** |
  | 量化回测 | 火候蛊 × 因果蛊 × 铺路蛊 × Python | 蛊材齐备（成本最低） |
  | 行业研究 | 先见蛊 × 火候蛊 × 投资学（沉睡） | 材料半备 |
  | 技术输出 | 铺路蛊 × 准绳蛊（写作）× 人言蛊（信道） | 缺信道 |

  > **知识地图**一箭三雕：产出一件作品 + 极可能是**阵道晋升「大师」**的事件（阵在你不在场时仍运转）+ 写作过程本身在**喂养濒死的人言蛊**。

  > **★ 选杀招的原则：兴趣优先于成本。** 当可投入的精力有限时，**兴趣是最可持续的燃料**。因此第一记杀招应选**最想做的那件**，而非材料最齐的那件。此原则以后固定生效。

  > **重复记录合并**：同一内容在多日反复出现（未决事项常被每日重抄），系统应识别并**只计一次道痕**。

### 4.8 空窍 / 真元 / 元石（状态与资源）

- **空窍**＝学习容量（有限，装不下所有东西；可扩容）
- **真元**＝精力（会耗会回）
- **元石**＝金钱（与精力同源，可互兑）
- 记录方式：**随手写两句**，**不打分**。
- 已知：**回元之法**＝运动 → 洗漱 → 补觉｜**耗元之源**＝低投入感的强制工作、高耗神的社交

## 5. 数据模型

```
records        id, ts, raw_text, source, created_at
evidence       id, record_id, type, source_type, weight, text, confirmed, created_at
evidence_dao   evidence_id, dao_id, weight           ← 一条证据可归属多道，权重守恒
daos           id, name, domain, layer, origin(原生/衍生/开创), realm_index, active, created_at
dao_parents    dao_id, parent_dao_id                 ← 衍生道的母子关系（如 智造道 ← 智/炼/器）
realms_log     id, dao_id, from_realm, to_realm, event_desc, evidence_id, achieved_at
gu             id, name, tier, kind, is_vital, fed_at, state
gu_dao         gu_id, dao_id                         ← ★ 多对多「相关」，**非隶属**
gu_feed_log    id, gu_id, action(养/炼/用), record_id, ts
killer_moves   id, name, status, materials(json), output_ref, created_at
aperture       id, date, essence_pct, mood_text, energy_note, stone_note
goals          id, name, type, linked_dao_id, next_action, status
knowledge      id, title, body, source, source_type, confidence, confirmed
knowledge_dao  knowledge_id, dao_id
interactions   id, type(测考/复述/因果检查), prompt, user_answer, ai_judgment, dao_id, ts
theme_pack     id, name, terms(json), visuals_ref
```

**关键约束**：
- `realms_log` **只能**由用户确认的晋升事件写入（R1）
- `evidence.weight` 求和 = 该道道痕，只增不减（R2）
- `gu.state` 由 `fed_at` 推导，不手工设置（R3）
- `knowledge.confirmed = 0` 的知识**不得作为事实引用**（R4）
- `aperture.mood_text` 只存文本，**不产出分值、不做诊断**（R5）
- **蛊与道是多对多「相关」关系，不是隶属**（R6）：一只蛊可服务多条道，一条道可拥有多只蛊，蛊可跨道复合使用——这正是**杀招**的由来
- **道分原生 / 复合衍生 / 开创三种来源**（R7）：衍生道记录其母道（`dao_parents`）；**开创道**是终极方向（对应无上大宗师）

## 6. 核心流程

### 6.1 记录（输入）
- 极低摩擦：Markdown 优先，支持粘贴、导入既有 `.md`
- 可自动打时间戳（用户不必手写日期）

### 6.2 结构化（AI 抽取）
从记录中抽取：`道 / 蛊 / 证据（道痕候选）/ 缺口 / 状态信号 / 杀招材料`
- **每条抽取结果必须带原文出处**

### 6.3 诊断
- 两轴定位（修为 vs 道境）
- 缺口发现：如"你懂某领域的实操，但没把对应的形式化方法接上"
- 组合发现：哪几只蛊可以合炼
- 状态读取：真元趋势、耗元来源

### 6.4 补强（★ 增强发生处）
| 机制 | 说明 |
|---|---|
| **AI 测考** | 用你的知识库出题，暴露"以为懂其实不懂" |
| **费曼复述** | 你把概念讲给 AI 听，讲不清就是没懂 |
| **因果检查器** | 你写下因果判断时，AI 追问：混淆变量？反向因果？反事实？ |
| **缺口追问** | 主动问缺的那块，不等人来问 |
| **跨域连接** | 把 A 道的知识连到 B 道（统计 × 心理 → 行为分析） |

### 6.5 验证
- 你交出产出（作品/复述/答案）→ AI 判定 → 成为**等级证据**
- **这是"水平"唯一的硬证据来源**（缺少外部裁判）

### 6.6 沉淀
- 回写：更新道痕、蛊的状态、知识卡、可能的晋升建议

## 7. 关键机制细则

### 7.1 境界事件判定
- AI 只能**提议**，用户**确认**后写入
- 提案必须附：事件描述 + 证据出处 + 为何符合该道本义

### 7.2 道痕计法与加权
- 默认各计 1；项目/复盘可按规模 1–3
- 权重由用户确认，AI 只建议

### 7.3 饿死衰减
- 由 `fed_at` 自动推导；「微饥」起轻提醒
- 沉睡的蛊可唤醒，但恢复需更多喂养

### 7.4 杀招合成建议
- 扫描"材料齐备但未合炼"的组合，优先提示
- **优先级 = 材料齐备度 × 与当前目标的关联**

### 7.5 知识可信度（防幻觉污染）
- 每条知识必须带：**来源**（你的记录 / 外部资料）+ **置信度** + **你确认与否**
- 未确认的标「待核」，不得当事实用
- **知识库被污染 = 系统报废**，这是第一优先级的工程约束

### 7.6 心理红线
- 只做**趋势与关联**（如"哪类活动让你变好"）
- **不打"心情分"，不做诊断，不替代专业帮助**
- 持续负面信号 → 温和提示并建议寻求支持

## 8. 界面

### 8.1 主面板（道为头，从上到下）
```
称号（修为 + 主修道境）        ← 两轴并排
今日一炼                      ← 每天只给一件事，带 5 分钟版
诸道 · 境界与道痕              ← 主区：境界由事件证明 + 道痕
所养之蛊                      ← 本命蛊 + 在炼的仙蛊
养 · 炼 · 用                  ← 三法与饿死时间表
可炼之杀招                     ← 组合价值
空窍                          ← 真元 / 心境 / 回元之法 / 元石
```

### 8.2 设计原则
- **干净、层级清晰、有顺序**：一条纵轴，不堆砌
- **首屏只给一件事**（今日一炼）——避免目标过载导致的启动困难
- **如实呈现，不羞辱**：0 天就说 0 天，并给出最小启动
- **境界不设进度条**：只有"当前境界 + 晋升须做成的事"

### 8.3 可选视图
- 技能树（道与蛊的依赖关系）、历史回放、周报入口

## 9. 风格包机制（产品一等功能）

**每个用户可选自己的世界观。** 事实层必须与世界无关，风格包只做命名与呈现。

```json
// theme_packs/gu-dao/terms.json
{
  "dao": "道", "gu": "蛊",
  "gu.mortal": "凡蛊", "gu.immortal": "仙蛊", "gu.vital": "本命蛊",
  "evidence": "道痕", "feed": "养", "refine": "炼", "use": "用",
  "starve": "饿死·沉睡", "killer_move": "杀招",
  "aperture": "空窍", "essence": "真元", "stone": "元石",
  "realm.0": "普通", "realm.1": "大师", "realm.2": "宗师",
  "realm.3": "大宗师", "realm.4": "准无上大宗师",
  "realm.5": "无上大宗师", "realm.6": "道主",
  "rank.4": "四转", "cultivation": "修为"
}
```

同一批字段，换一个风格包就是修仙的"境界/神通"、科幻的"文明等级/模块"。**事实一个字不变。**

## 10. 冷启动

1. **引导访谈**：AI 主动问（已产出 `访谈_个人发展补全_v1.md`，22 题）
2. **从既有记录反推**：能推的不问（如从 `task.md`/`记事本碎.txt` 推出统计、建模、因果倾向）
3. **渐进补全**：之后每次对话顺带问 2–3 个缺口，不要求一次填完
4. **先问推不出来的**：心理状态、兴趣、目标、时间预算、记录偏好

## 11. 非目标（首版不做）

- 全自动知识图谱（Neo4j 等）——首版用 SQLite

## 12. 验证方案

| 验证项 | 标准 |
|---|---|
| **溯源准确性** | 抽取的每条结论能否对上原文；用户主观准确率 ≥ 85% |
| **洞察有效性** | 建议是否切中要害、是否提供没想到的视角 |
| **晋升守规** | 晋升是否**只在事件真发生时**触发；有无自评虚高 |
| **增强是否发生** | 测考/复述是否真的暴露了"以为懂其实不懂" |
| **留存** | 用户是否愿意持续记录（最低标准：不断更） |

### 首轮真实验证结果（2026-09-04）

拿 `task.md` + `记事本碎.txt` 跑了一遍抽取与诊断，用户逐条核对 18 项：

- **准确率 13/18 = 72%**（部分对折半计 78%）——**未达 85% 标准**
- **错因高度集中**：5 条误判（3 不对 + 2 部分对）**全部**源于同一错误——**把"文件里出现的内容"当成了"本人的能力"**
- **修正**：新增 §4.4 的「抽取三分类」前置闸门；`evidence` / `knowledge` 增加 `source_type` 字段
- **意外收获**：暴露出一个真实缺口——用户想建一张**知识地图**（把随手记的知识串联起来），已立为杀招

> 结论：**抽取环节基本可用，问题出在"归属判定"**。这条教训比准确率本身更值钱。
